# 中文博客文风

根据文章的目的和读者调整篇幅。技术博客保持论证严谨，允许用第一人称记录观察、调研与设计过程；日常随笔保留作者原有的语气和节奏。尊重用户明确给出的受众、用途、范围和修改意见。

写作或润色前阅读 [文风样本](references/examples.md)，参考其中的叙述节奏、技术解释和图文配合。文章落点和 frontmatter 按 [note-prose](../note-prose/SKILL.md)；Markdown 组件按 [note-markup](../note-markup/SKILL.md)；图的格式和文件位置按 [note-figure](../note-figure/SKILL.md)。

## 叙述与节奏

- 面向没有读过项目源码或内部文档的读者。先交代背景、具体问题和影响，再引入方案；术语首次出现时，结合它在文中的作用解释。
- 技术设计文章沿着实际问题、调研、取舍和实现展开。先介绍参考方案解决什么、如何工作，再写作者受到的启发或决定。第一人称用于有根据的观察与思考，事实不明确时核对材料，不虚构经历或对话。
- 一段推进一个意思，句子中的主体、动作和因果关系要明确。同一句话里，前后分句的主语尽量保持一致。时间或条件从句省掉主语时，省掉的就是后半句的主语：写「获取结果之后，模型再看数据、决定下一步」，不要写「结果回来之后，模型再……」。前一种的隐含主语仍是模型，后一种把主语换成了结果。连着发生的动作放在同一句里，用逗号接上。观点发生转折时，用独立段落承接前文并引出后文，写明转向的具体问题。
- 多个观点处于同一层级且需要分别解释时，先用一句有信息量的话总起，再用列表逐项展开；每项以完整的陈述句指出该点，适当加粗关键观点，后接依据或例子。共同结论放在列表之后。复杂机制可用例子、图和代码展开；读者已能理解的限定和背景不重复解释。
- 正文用陈述句。章节标题用这一节的机制名，或带简单修饰的主语，如「检查点与恢复」「前缀缓存」「整套 harness」。不要把一句话压成标题。「结果留在程序里」「分数来自整套 harness」，以及「甲在乙里」「甲来自乙」这种压缩句，都不是标题：它们没有说出机制的名字，也不是正常的动宾或主谓宾。只有问题本身需要讨论时才使用问句，不用设问制造过渡。
- 探索过程可以有个人色彩，但以实际观察和选择推进。删去「还要多问一句」「容易错过的是」等不带信息的引导，以及与前文重复的免责声明、版本提示和总结。

## 用词

- 正文用中文顿号 `、` 分隔并列词语, 顿号后不加空格, 例如「题目、交互和评分」. 分隔分句的逗号以及句号、问号、感叹号、冒号、分号用半角符号, 后接一个空格; 段落末尾、闭合引号或括号前无需添加尾随空格. 括号和引号用半角. 英文缩写、小数、版本号、网址、代码及 Markdown 语法保持原样, 避免改变含义或渲染. 标题、说明文字与图注同样遵循此习惯.
- 货币金额用「美元」或 USD, 不用 `$` 与数字连写. 主题 Markdown 管线会把 `$` 当公式定界符, 详见 [note-markup](../note-markup/references/theme.md) 的公式一节.
- `src/content/blog` 与 `src/content/shorts` 正文不用直角引号 `「` `」` 包裹词语或短语做强调、贴标签或代指机制; 机制名用反引号、英文专名或直述. callout、图注与章节标题同样遵守.
- 用自然、准确的书面中文，保持直接和克制。具体写清动作、状态和结果，避免含义不明的套话和未经解释的项目内部简称。
- 机制用已经定义的术语，不用比喻动词代替动作。模型在程序里发起工具调用，写「在 Script 里调用」「由 `execute` 发起调用」，不写「包住」「包进去」。一次会话的第一次模型请求写「首次请求」，不写「首包」。
- 区分口语化和自然表达：技术事实优先用精确说法。例如「重新执行需要承担额外的时间与 token 成本」，而非「前面的时间和调用又得再花一遍」。日常随笔可以保留作者自己的口语。
- 作者写轻松随笔时, 会用 `~~划掉的说法~~` 或括号里的旁白 `(……)` 表达幽默、吐槽或随性的语气. 润色时保留文中已有的这类写法, 不要为了「更正式」整篇删掉; 未经作者明确要求, 不要自行添加 `~~……~~`、括号吐槽或类似口气.
- 用肯定句直接陈述实际关系，避免无必要的对比。限制只在影响理解、使用或事实准确性时说明，写出限制的具体后果。
- 避免含糊关系词。写「恢复后的工作目录应包含会话中已经完成的文件修改」，而不是「让上下文和文件对应起来」。专业术语可以使用，但第一次出现时解释其具体对象。

## 技术讲解与证据

- 先确认文章目的：介绍设计与原理时，围绕触发条件、输入状态、处理顺序、结果和失败边界展开；只有读者需要使用时才展开命令、参数和版本差异。
- 查阅原文、源码和相关设计材料，区分已经实现的行为、提案、实验结果与尚未验证的设想。涉及版本或时间线时准确归属；只呈现与文章论点或读者判断有关的细节。
- 描述机制时讲出关键分支和数据流，不能只列功能名称。选择能解释原理的简短代码或流程图，并说明代码前后的状态变化和设计原因。
- 引用真实源码时，核对仓库、版本、文件和行号，优先用 [note-markup](../note-markup/SKILL.md) 的代码卡片。表达经过简化或组合的流程时，明确写「下面的伪代码展示了……」，不要让读者把示例当成原始源码；在关键分支旁加简短注释。伪代码不能暗示未核实的保证或实现步骤。
- 引入代码时直接说明它展示的流程；代码后解释读者需要理解的边界或结果。相关术语在示例前后解释，避免用长串内部变量名代替讲解。

## 图与正文

- 图要补充正文：用简短节点表示对象、状态或结果，用箭头和贴近线段的文字表达操作、条件或转移。避免把段落缩写后塞进节点，也避免只有功能名称而没有关系。
- 文字和默认线条按 [note-figure](../note-figure/SKILL.md) 的亮色原稿书写，可用柔和填色区分节点。暗色显示由预览器转换。参考图提供了线条风格时，按其视觉语言绘制，并保持箭头与标签分开。
- 检查图是否表达正确的关系，尤其是分支输入、环境和结果；检查文字与箭头、节点是否重叠。按 [note-figure](../note-figure/SKILL.md) 在页面中检查图的默认视图、缩放与可读性。

## 交稿前通读

按读者顺序通读全文，不要只改用户点名的那一句。检查：问题是否具体、每段是否推进内容、同一句话的主语是否前后一致、关键机制是否有依据、代码和图是否帮助理解、正文里是否误用 `$` 表示金额。用户指出一处问题时，把全文里的同类句子一并改掉。删掉重复说明、无信息量过渡和未经请求的用法细节，同时保留其他内容与作者声音 (含 `~~……~~`、括号旁白等已有轻松语气).
