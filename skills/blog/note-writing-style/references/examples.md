# 中文博客文风样本

这些片段展示句子的节奏和讲解方式. 人物经历、时间、机制和示例数据以当前文章的材料为准; 写作时借鉴方法, 避免照搬句子.

## 具体问题与成本

> ageval 让任务脚本负责描述题目、交互和评分, 再用插件选择模型、Agent 运行程序和执行环境. 同一道题可以在相同的评分条件下, 更换模型或运行程序做对照.
>
> 随着 Agent 能处理更长的任务, 运行中断的成本也随之增加. 假设 Agent 已经读完代码、写了一半程序, 主进程却因为断线或机器重启退出. 未完成的题目需要恢复进度; 如果重新执行, 就需要承担额外的时间与 token 成本.

先让读者知道框架做什么, 再写故障发生时损失了什么. 例子服务于问题; 数字只解释与论点有关的含义.

## 参考方案与个人思考

> 十月初, 我看到了 Pi Durable. 它把模型调用、工具执行等工作组织为任务, 并在执行过程中保存进度. 进程重启后, 它会找到尚未完成的任务继续处理.
>
> 我开始考虑把这种恢复机制引入 ageval. 评测还需要保存 Agent 工作时的环境: 除了对话, 仓库里已经修改的文件、执行命令产生的结果也需要恢复.

先介绍被参考方案的机制, 再写它引出的设计问题. 第一人称记录实际的思考, 不单独用设问充当过渡.

## 把状态关系写具体

> 恢复时, Agent 需要接着之前的对话工作, 看到的文件也应当处于那段对话结束时的状态. 如果原环境里还有命令正在运行, 恢复过程还需要处理这条命令.

这段话指出恢复时各状态应该是什么样, 以及正在运行的命令带来的额外处理, 比"上下文和文件对应起来"更容易理解.

## 并列情况分点说明

不同 Agent 的会话管理方式也不同:

- 对于由 ageval 在**宿主进程里管理**的对话, 恢复时会读取日志中最近一次完成的压缩记录, 用摘要替代记录中指定的旧消息, 再接上之后的模型回复和工具结果.
- 有些 Agent 在**环境内维护**自己的会话文件, 恢复时则使用检查点中的会话文件继续, 由该 Agent 恢复压缩后的上下文.

无论采用哪种方式, 恢复后的工作目录都需要反映会话中已完成的操作.

用引导句指出比较对象, 每项解释一种情况, 再在列表后说明共同要求. 加粗各项的区分点, 让读者能够快速找到差异.

## 转折与并列观点

> Git 可以保存文件在不同时刻的状态. 我们可以在每次工具调用结束后创建提交, 再把提交 ID 写入活动日志, 供恢复时查找文件版本.
>
> Git 能提供文件版本和差异查看能力. 将它用于评测恢复, 还需要处理任务仓库、会话文件、文件权限和敏感信息等问题.
>
> 1. **检查点不能随意写进任务自己的 Git 历史**. Agent 可能依赖仓库状态完成任务, 检查点提交会改变它看到的历史.
> 2. **恢复进度需要工作目录之外的文件和活动日志**. Agent 的会话记录可能保存在 home 目录, 文件版本也需要与日志中的进度关联.
> 3. **Git 的普通文件模式无法覆盖所有权限变化**. 它能记录可执行位, 但无法区分 `0640` 和 `0600`.
> 4. **凭据和敏感信息需要在写入存储前处理**. 文件进入对象库后, 从工作目录删除它也不一定会清除历史内容.
>
> Git 可以作为文件快照的存储后端, 日志关联、快照范围、权限和过滤规则仍需要由评测系统处理.

先说明方案, 再用独立段落承接其能力并引出具体限制. 四点是同一层级的理由, 因此放在同一个列表里; 每点开头直接陈述观点, 后面解释原因. 列表后再写共同结论.

## 伪代码与解释

> 对于未能收回结果的中断步骤, 系统会根据调用类型和工具的重试许可决定下一步. 下面的伪代码展示了这些分支:

```python
if step.kind == "model_call":
    mark_aborted(step)
    resend_model_call()
elif step.replay_safe:
    rerun_tool()
else:
    # 将已有输出和中断信息交给 Agent
    return_interrupted_result(step.partial_output)
```

> 只有明确标记为可安全重复的工具才会自动重试; 其他工具会把中断信息和已有输出交回 Agent.

伪代码是对所述机制的概括, 函数名为说明流程而设. 实际文章应核对条件和源码, 代码前直接说明展示的流程, 代码后讲清关键分支的含义.

## 从记录到执行

> 轨迹保存模型响应、从响应中解析出的动作, 以及执行后得到的观察. 重放时, 系统按顺序取出记录的响应或工具调用, 交给 Agent 循环; Agent 执行动作, 再从当前环境获得新的观察.
>
> 重放使用已有记录, 无需再次请求待测模型. 初始文件、依赖或外部服务发生变化时, 同一动作也可能产生不同结果.

按"记录了什么 → 重放读取什么 → 环境产生什么"讲解, 说明模型和工具各自参与的环节. 描述具体项目时应核对其实际实现.

## 同一句话的主语

时间或条件从句省掉主语时, 省掉的就是后半句的主语. 连着发生的动作放在同一句里, 用逗号接上.

| 写法 | 示例 |
| --- | --- |
| 正例 | "获取结果之后, 模型再用自然语言看数据、决定下一步, 五次工具就是五次推理." |
| 反例 | "结果回来之后, 模型再用自然语言看数据、决定下一步. 五次工具就是五次推理." |

"结果回来之后" 的主语是结果, 下一分句又换成模型. "获取结果之后" 省去的主语仍是模型, 和后半句一致. 看数据、决定下一步, 以及因此发生的五次推理, 是同一件事, 不要拆成主语各不相同的两句.

## 标题和引导句

章节标题用机制名, 或带简单修饰的主语. 正文里的陈述句留在段落中, 不压成标题.

| 写法 | 示例 |
| --- | --- |
| 机制名 | "检查点与恢复", "前缀缓存", "分页搜索" |
| 带修饰的主语 | "整套 harness", "Pi 的 codemode" |
| 反例: 把一句话压成标题 | "结果留在程序里", "分数来自整套 harness" |
| 反例: 「甲在乙里」「甲来自乙」 | "状态在日志里", "成本来自重试" |

"结果留在程序里" 和 "分数来自整套 harness" 没有说出这一节的机制, 也不是正常的动宾或主谓宾. 这一节若在讲过滤和提前退出, 标题写 "过滤与提前退出"; 若在讲成绩所衡量的整套程序, 标题写 "整套 harness".

引导句仍是完整的陈述句:

| 写作目的 | 示例 |
| --- | --- |
| 引入外部方案 | "Inspect 在回合边界检查是否需要写检查点." |
| 引入伪代码 | "下面的伪代码展示了环境探测、接回和重建的判断过程." |
| 说明提案范围 | "Harbor 的恢复 RFC 提议通过环境句柄接回仍在运行的环境." |

提案状态、版本或失败边界在读者需要时交代一次, 后续段落继续解释具体机制.
