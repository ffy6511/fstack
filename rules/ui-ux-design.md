# UI / UX 设计与交付规范

适用于新建界面、改进已有产品、复刻参考应用，以及嵌入宿主的工具页。先遵守用户指定的参考和项目设计系统；以下规则用于指导设计判断、实现和验收，不要求所有产品长成同一套模板。

## 1. 先理解用户怎样工作

- 先确定使用者、当前任务、最常见操作和完成条件，再决定页面结构。不要先堆组件，再让用户适应现有布局。
- 从完整用户流程考虑：如何进入、选择、查看、比较、深入、返回和继续。主流程涉及的上下文应连续保留。
- 区分主要内容、次要信息和操作入口。浏览页应把空间留给内容；分析输入框、配置表单和提示不能抢占主区域。
- 对已有产品的改进应保留熟悉的交互，除非用户要求改变，或已确认原交互存在问题。

## 2. 认真使用参考，不做表面近似

- 用户指定参考应用时，先读它的组件、样式、交互和真实数据解析。有条件时实际打开参考页面。
- 对照信息结构、筛选方式、列表密度、整行点击、选择控件、指标图形、详情展开、弹窗和返回路径，不能只核对字段和 API。
- 优先复用已有组件或迁移其实现。需要适配容器尺寸时，保留原来的操作语义和视觉层级。
- 不要把“能读取数据的最小面板”当作完整 Viewer，也不要用功能名相同的简化实现代替用户要求的复刻。
- 参考文档中的平台假设要核实：原生表单是否已预设样式、图标字体是否存在、CSS variables 是否可用，都不能凭空假定。

## 3. 组件与视觉必须统一

- 优先使用项目已有的设计系统；需要新增时，建立共享组件和样式，不在每个位置分别实现。
- 选择器的触发器及其展开菜单都要自定义并统一风格。不能只美化按钮，却保留系统原生下拉菜单。
- 同类控件共用高度、圆角、边框、字体、图标、内边距和状态样式。主操作、次操作、危险操作应有明确区别。
- 同时设计默认、悬停、焦点、选中、禁用、加载和错误状态。使用颜色表达含义时，还要提供文本或图形标记。
- 主题颜色、表面、边框和文字优先使用设计 tokens；嵌入式界面遵循宿主的 CSS variables，检查明暗主题。
- 默认采用平整、清晰的表面、细边框和克制字重，不用渐变、阴影和装饰掩盖结构问题。用户指定的视觉方向优先。
- 图标应使用统一图标库，尺寸和对齐一致。装饰图标不重复朗读，纯图标按钮有明确的可访问名称。

## 4. 紧凑，但不能贴边或挤压

- 根据内容设置合理最大宽度和左右 padding。宽屏不无限拉长行，窄屏也保留基本边距。
- 工具栏、列表、详情和底部操作区使用一致的对齐线。区分容器留白和行内 padding，避免只有标题有边距，列表内容却贴边。
- 给主要内容足够空间，同时保持克制的呼吸感。不要用巨大输入框、大面积空白或过度分散的卡片稀释信息密度。
- 长路径、模型名和标识符必须有明确的截断或换行策略。保留查看完整值的方式；截断文字时不能连图标和操作入口一起裁掉。
- 在 flex/grid 中明确可伸缩区域和固定区域：文本允许收缩，必要图标与箭头不参与压缩；检查 `min-width`、`max-width`、`overflow` 和规则优先级。
- 长选项不能撑大选择器，次要控件不能挤掉主要入口。不要依赖一条通用 `width: 100%` 解决所有控件布局。
- 弹层不能被父级滚动容器裁切。靠近屏幕边缘时调整位置或方向，保留边距，限制高度并允许内部滚动。

## 5. 操作对象清楚，选择结果可管理

- 列表项有详情时，默认整行可点击，提供悬停、焦点和键盘入口，不把点击范围缩到一小段文字。
- checkbox、选择器、菜单和行内按钮应隔离事件，不能因选择操作误触发行跳转；键盘事件也要检查冒泡。
- 已选数量应能打开已选项列表，让用户核对、逐项取消；数量不能只是一个无法操作的标签。
- 筛选、搜索和选择状态应可辨认、可撤销。切换数据源或范围后，清理已失效的选择，避免把旧上下文带进新操作。
- 常用路径或对象保存后应能快速重新打开，不让用户反复输入同一组配置。
- 弹窗有明确标题、确认或取消入口；支持 Escape、合理的焦点管理和关闭后焦点恢复。按操作风险决定是否允许点击外部关闭。
- 下拉菜单支持方向键、Enter、Escape 和合理的焦点行为；长列表可滚动，长标签仍可辨认。

## 6. 数据展示要帮助判断

- 先呈现用户用于决策的指标，不把所有底层状态码都放进列表。冗余的 status 应移到详情或省略。
- 选用与指标含义匹配的图形，并沿用参考产品的约定。例如通过率可用蓝色圆环加数值；不要用无意义装饰替代指标。
- 数值按用途格式化，避免直接显示浮点长尾。界面保持适当精度，详情、悬停或复制仍可获得原值。
- 缺失、失败、加载、空结果和截断必须区分；未知值不能显示成零。显示的数量应与可查看的数据一致。
- 对日志、对话、轨迹和其他结构化证据，先采样真实数据再设计 renderer。原始 JSON 或一个长文本框只能作为原始数据视图。
- 正式证据视图应表达结构：角色、步骤、工具调用、观察结果、时间和错误；长内容提供预览、折叠和展开，必要时支持类型筛选与定位。
- 操作过程和最终结果分开表达。不要凭日志里的自述、进程状态或轨迹内容推断业务已成功。

## 7. 实现应便于持续修改

- 使用 TypeScript 和独立 CSS 维护复杂界面，将通用控件拆成组件。不要长期把整页堆在内联样式、超长表达式或字符串中。
- 构建产物由脚本生成；修改源文件后通过正式构建流程更新，避免源文件和实际加载代码分离。
- UI 状态、数据读取和展示组件适当分离；本地、远程等不同来源尽量共用展示和业务解释，避免同一字段出现两套解释。
- 浏览轻量证据时按需读取，不为展示少量内容下载整个工作区。显式说明数据来源、读取上限和新鲜度。
- 异步请求要处理加载、失败和返回顺序，避免旧请求覆盖新选择。保存、切换和重载后检查用户配置与上下文是否保留。

## 8. 验收完整流程，不让用户代做第一轮测试

- 编译、类型检查、单元测试和 API 验证分别说明各自覆盖范围。它们都不能代替实际页面检查。
- 使用真实或有代表性的数据，实际点击主流程；检查长文本、空结果、多选、弹层、详情和返回。
- 检查宽屏与窄屏、明暗主题、鼠标和键盘。关注图标完整性、左右边距、文字溢出、菜单越界及选中状态。
- 修改后确认页面实际加载了新代码。不要未经检查就把用户看到的问题归因于缓存，或反复让用户刷新来代替排错。
- 优先通过局部重载、HMR 或页面刷新更新，不能为验证一个界面随意关闭宿主、杀进程或重启应用，打断用户的其他任务。
- 若认证、权限或环境限制阻断实际页面验收，继续完成独立可做的验证，并准确标注未验收范围。组件测试通过不能写成宿主页面已通过。
- 用户给出截图后，定位具体布局、样式或交互原因，修正同类位置；不要只遮住当前症状，也不要以道歉或计划代替继续处理。

## 交付前检查

- 是否逐项核对并保留了参考应用的关键结构和交互？
- 控件与展开菜单是否统一，所有状态是否可辨认？
- 左右 padding、最大宽度、图标与长文本是否在宽窄屏都正常？
- 行点击、控件事件隔离、已选项查看与取消是否可用？
- 指标和证据是否真正渲染，还是只展示了原始数据？
- 实际加载的新页面是否经过操作和视觉检查？哪些项仍未验证？
- 更新是否保留用户配置，且没有打断其他正在进行的工作？
